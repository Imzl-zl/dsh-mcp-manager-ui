## 跨行教训（只记不变量级的；单行细节在 TODO.csv 的 notes）

1. **「看到红」不等于「测到了」**：夹具在 setup 阶段报错也会红，断言根本没执行（本机缺符号链接权限，只有目录 junction 能建）。**第二个实例（2026-10-11）**：`test/skills-host.test.mjs` 那条「导入落点」用例自 `8367f62` 起一直红在两个缺失导入（`existsSync`、`readdir`）上，补完导入才露出夹具漏建只读根 `bundled`——三条断言里最后那条（「内置根不得被写入」）从来没执行过。同一个 `ReferenceError` 被当作「既有失败」带过了好几轮；看到红的第一件事是确认断言到底跑没跑到，而不是先记成环境问题。
2. **变异存活时先怀疑变异，再怀疑测试**：一个「不可能失败」的变异和一条「永远通过」的用例是同一类错误（删掉断言自己就是同义反复）。
3. **别用自己改写的「代表性文本」当夹具**：那测的是想象而不是真实世界。许可判定必须用逐字原文，并同时用 MIT/BSD/Apache 原文测「不得误杀」。
4. **同一件事只能有一处判据**：两处判据会在改名/重构后分叉，而静默失效的那一处往往正是闸门（让位检测的自身排除）。
5. **定义基准的测试不能参与被测的那次改动**：旧名常量必须显式写死，否则改名脚本会顺手改掉判据。
6. **要测「必须同时满足」，只能用只满足一半的输入**。
7. **有缓存的被测对象，用例之间必须显式清缓存**，否则「测第二条」其实在测第一条（远端搜索的 5 分钟缓存）。
8. **手抄的清单会漂**：契约完整性要由 `@Remote` 标记机器推导；`remoteMethods()` 要**活实例**、不是 prototype（传 prototype 得到空数组，`deepEqual([], [])` 照样通过）。
9. **「无悬空引用」这类承诺必须是闸，不是散文**：现由 `test/tasks-spec-integrity.test.mjs` 守着。
10. **替换锚点要包含被保留的部分**，只用目标行做锚点会把它一起吃掉（曾误删 `const h = React2.createElement`）。
11. **引用一个「应该是既有」的东西前先确认它真的存在**：凭想象写 `readWorkspaces()` 会静默走错路径。
12. **常驻的计数类断言用下界**（样式前缀 `> 500`），钉死数字会让每次加样式都要改测试。
13. **测「宿主给我们什么」这件事，必须用真宿主包；手搓的 fixture 是我以为的宿主形状**（2026-10-12，本仓库付了两次代价）。`@deepseek-ai/dsh-skill-filesystem` 原先**不在 devDependencies** 里——而它正是决定「`resourceBase.path` 是展示路径、`path` 是 realpath」的那个包。于是所有技能用例都喂手搓 summary，整类缺陷（链接技能全不可操作）测不到，真机上由用户报出来。补上依赖后，新增用例用真 cordis + 真宿主包 + 真符号链接，一次就把「停用后消失」「删除报错」都逼出来了。**判据**：只要断言的输入是「宿主产出的值」，就问一句——这个值是我构造的，还是宿主真的会这么给？
14. **断言要落在「用户能不能用」上，不能落在「界面显示了什么」**：同一批缺陷里，列表长度、徽章文案、根目录字符串**全都对**，而用户点下去没有任何反应。显示层用例再多也拦不住这一类；每条操作都要**真的改到盘**（启停后文件真的改名、删除后外部库真的还在）。
15. **缺陷要按「形态 × 操作」矩阵找，别只按用户报的那条找**：用户报「符号链接目录」，而同一根因还覆盖「扁平技能的文件本身是链接」（本机建不了 file symlink，只有宿主源码的用例里看得见这种形状）。**从宿主源码的测试与 README 里读「有哪几种形态」，比自己想可靠**。
16. **发布前要拿「已发布产物本身」验收，不能拿工作树冒充**（2026-10-12）：本轮一度把工作树文件复制进「已发布产物」目录又去跑验收，结论因此失真。正确做法是解包 npm tarball、按生产布局（peer 为兄弟目录）摆好，再跑同一套脚本——本轮的 1.6.4 对照（0/11 vs 11/11）正是这么得出的。
13. **闸的覆盖面本身也要被断言**：`package-rename` 的目录扫描首版只 `readdir` 一层，`.github/` 的子目录（release notes 与 workflows）整类无人看管——于是「v1.6.0 发布稿把旧包名当主安装路径」和「release.yml 把 Release 标题写死成旧包名」两处真错留了好几轮。改成递归之后又发现第二层问题：白名单按**行的形状**放行「`dsh plugin … add <旧包>`」= 把「叫用户装旧包」和「教用户从旧包迁过来」判成同一件事，前者正是缺陷形态。修法是让迁移说明靠**同行的措辞**（旧包 / 此前叫 / 迁移）放行，安装命令本身不再有豁免，并做变异验证（塞回旧命令 → 闸红且精确点名）。
14. **「改一处、露一处」出现第二次时，就该停下来找不变量，而不是修第三处**（2026-10-12）：技能面连爆三次——「技能目录是链接」→「扁平技能的文件本身是链接」→「文件名与技能名不一致」，每次都只换一处判据。真正的不变量是**身份与定位分家**：`name` 只用于显示与指认，位置永远来自宿主报告的字段。用户的原话点破了它：「结构性问题做结构修复，不要加特例补丁——先找共同的不变量再动手」。**判据**：同一个根因的第二次出现，就是「该找不变量」的信号，第三次出现说明前两次修的是症状。
15. **自创机制要先问「宿主有没有原生等价物」，再问「它优雅吗」**（2026-10-12）：技能面的「停用」一直是自创的（改名成 `SKILL.md.disabled`），而宿主**原生**支持的两个调用面字段组合起来就是「停用」——还是 VS Code 官方文档里叫 “Disabled skills” 的那一档。自创机制的代价不是「不好看」，是**它会外溢**：`~/.agents/skills` 是 Agent Skills 标准的共享位置（VS Code / Codex 都读），改名等于为了本面板一个开关在**别的工具里**把用户的技能弄坏。调研方法：**先查主流怎么做**（第一方产品里零个用改名，只有第三方社区工具这么做），再回宿主源码确认原生支持什么。⚠️ 反过来说也成立：主流这么做**不等于**我们该这么做——判据始终是「宿主支持什么」，主流只是用来发现自己漏看了什么。
16. **验收脚本自己也要被怀疑一次**（2026-10-12）：`_accept.mjs` 本轮自己出了三个 bug——把快照取在停用**之后**（于是「逐字节还原」三条假红）、把 peer 链接建在 `npm install` **之前**（链接被覆盖，报一个看不懂的 `ERR_MODULE_NOT_FOUND`）、`.catch()` 把建链接的真实错误吞掉（静默退化让报错指向完全错误的地方）。三个都修好之后结论才可信。**判据**：验收脚本报红时，先确认「是产物错了还是脚本错了」——把失败原因打印得足够具体（哪个文件、什么状态），别让它只说「失败了」。
17. **变异存活时，先怀疑变异体与原实现是否等价**（2026-10-12，教训 2 的实例）：本轮 9 项变异里有一项最初**假存活**——变异体去读 `input.name`，而调用方**从不传** name，于是它与原实现完全等价，用例当然全绿。修好变异体之后立刻变红。另一项（`locateSkill` 的条目改用 `path` 末段）在本机**真的不可分辨**：文件符号链接是 EPERM、而 `realpath` 会把大小写归一，所以「扫出的条目名」与「path 末段」在能造出的任何形状里恰好相同。这种情况下正确的处置是**如实写下空白**（断言可构造的那一半：证实不了就不填根），而不是写一条永远跑不到的分辨断言——那只会制造「看起来测到了」的假象。
18. **「校验比宿主更严」会制造整页级故障，而不只是一行不可用**（2026-10-12，审查拦下）：本轮我加了「拒绝 `kind: bundle` + 条目以 `.md` 结尾」，理由是「宿主会把 `.md` 结尾的目录当扁平技能」——**理由反了**（宿主 `discoverRoot` 目录分支优先，`odd.md/` 完全合法）。它让 `resolveSkillTarget` 抛错 → `list()` 整个 reject → **技能页整块打不开**，连健康的技能都管不了。两条纪律：① **判据不得比宿主更严**，磁盘条目名不归宿主管；② **列表类 RPC 不许被单条数据的错误整死**——单点容错要在读那一行的地方做，不能指望「上游一定不出错」。⚠️ 这条尤其值得记：同一个「自洽性校验」在**单条操作**上的代价是「这一行不可用」，在**列表**上的代价是「整页不可用」，量级完全不同。
19. **机制换代时，「读」和「写」必须一起换代**（2026-10-12，审查拦下）：本轮把「停用」从「改名」改成「写字段」，但**迁移读取**这条支线只换了读——它把旧残留列出来了，却没实现「恢复」的写路径（`setSkillEnabled` 只写字段、从不 rename，而残留的停用状态在**文件名**里）。结果是 UI 上写着「点启用把它改回来」、点了报成功却什么都没发生。**判据**：凡是「为了兼容旧状态而保留的读取路径」，都要问一句「这条路径上的**动作**也跟着换代了吗」——只读不写的兼容层等于把用户骗进死胡同。
20. **发布前让一个独立审查者先跑一遍，比再多写十条用例都值**（2026-10-12）：本轮 554 条用例全绿、变异 9/9 命中、验收对照 33/33 vs 9/32 —— 而独立审查仍然用**它自己的探针**找出 3 条 Critical（两条会让整页报错或按钮点了没反应）。原因不神秘：**写代码的人和自己写的用例共享同一套盲区**（我没想到「目录名以 .md 结尾」，因为我脑子里的形态集合里没有它）。⚠️ 用法上的两点：① 给审查者的简报要写清「不变量是什么、哪些已核实过」，否则它会把时间花在重跑你已经验过的东西上；② 它报的每条都要**自己先复现再改**——本轮它报的 3 条我逐条复现，全部成立；同时它明确列出 10 项「已核实非问题」，让我没有去改本来就对的地方。
21. **能起真机就别搭间接工具；而且必须在隔离数据上起**（2026-10-12，本轮教训，两半都重要）：用户一句「你为啥不启动 web 端测试看看」点破了 —— 我只查了**正在跑的** desktop profile（装的是旧包、没有技能面）就下结论「真机看不了」，转而去搭离线渲染页；而 `skillsuitest` profile 本来就 `link:` 到本仓库，起一个实例只要一条命令。**真机一次就抓到离线预览抓不到的缺陷**（诊断行把整条根路径塞进 185px 副标题 → scrollWidth 237 > 185 → `.dsh-mcp-item-sub` 没有 ellipsis → 硬裁成半截「已」）。离线预览只值得在**真机起不来**时用。
    ⚠️ 另一半更贵：我第一次是拿**用户真实的技能库**点的，一个点击把 `deepseek-harness/.agents/skills/dsh-translate-docs/SKILL.md` 里两行删掉了（已用备份 + git 双重还原、哈希核对一致）。**审 UI 的破坏性动作必须先在隔离的 `DSH_HOME`/`DSH_AGENTS_HOME` 上做**（profile 用 junction 共享即可，插件仍指向工作树），临时目录用完即删。同轮还发现：写「根路径不得出现在副标题里」的用例时，第一版**测错了对象**（渲染 `SkillRow`，而诊断行是**内联在 `SkillsPanel` 里手写**的、不走 `SkillRow`）——变异注入后仍全绿，改成渲染真 `SkillsPanel` 才拦得住。**变异存活先怀疑用例没走到那段代码**，与教训 17 是同一枚硬币的两面。
